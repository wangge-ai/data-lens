# 连续经营表格分析方法

适用于按日期或批次反复导出的经营数据，覆盖平台、店铺、商品、推广、库存、退款和履约等对象。这不是普通的“概括几张表”，而是先建立可重复计算的经营事实层，检查各批数据能否比较，再解释发生了什么变化。

## 要回答的问题

按以下顺序回答：

1. 总体经营水平和每日走势如何？
2. 哪个阶段或平台对变化贡献最大？
3. 变化主要来自订单量、每单支付、结构、退款售后、推广、库存覆盖，还是资料覆盖变化？
4. 聚合全部合格记录后，哪些店铺或商品变化最大？
5. 哪些日期只是待核验的突变或数据质量候选？
6. 运营人员现在、接着和以后分别应该核查什么？

## 怎么识别这类资料

强信号是至少三个日期批次，或同一类表格跨日期重复出现，同时含有订单、支付额、件数、推广支出、退款、库存、出库或履约等字段。

先用 `scripts/inventory_inputs.py` 识别采集日期和重复表格家族，再运行 `scripts/plan_analysis.py`。文件夹里的日期只能作为采集日期提示，不能自动当成订单日期、推广日期、退款日期或库存日期。

## 平台适配边界

核心方法不得写死平台名称或供应商列名。每个导出表家族需要一份经过审核、带版本号的适配规则，把原始列映射成下面的标准事实。适配器名称和版本保存到运行清单。无法确认的列保持未映射，不能根据数字大小猜字段。

解析新文件前先运行 `scripts/prepare_operational_run.py`。只有来源哈希、解析器版本、指标版本和完成状态全部一致时才能复用旧结果。旧版 `.xls` 通过 `scripts/parse_tabular_exports.py` 的持久转换缓存处理。

## 时间口径

分别声明适用的时间轴：

- `collection_date`：文件或导出批次的采集日期；
- `business_date`：订单或支付表现所属日期；
- `promotion_date`：推广事件日期；
- `refund_date`：退款记录日期；
- `snapshot_date`：库存快照日期。

不能因为日期字符串相同就直接关联不同时间轴。库存快照只能说明当时可见的库存，不能重建历史库存。推广支出和支付额只有在平台、归因窗口和日期口径兼容时才能比较。

短窗口先描述时间点、变化和局部趋势。没有明确起止指标和足够历史覆盖时，不把十天或二十天命名为完整阶段、周期、旺季、衰退或恢复。历史分位数也不能单独确定周期位置。

## 标准事实层

确定性分析脚本接收 `corpus_lens_operational_facts/1.0` JSON。下面为了简洁省略了来源位置，但真实适配结果必须保留原始文件和行号。

```json
{
  "contract": "corpus_lens_operational_facts/1.0",
  "time_contract": {
    "platform_daily": "business_date",
    "promotion": "promotion_date",
    "inventory": "snapshot_date",
    "files": "collection_date"
  },
  "periods": [
    {"id": "earlier", "start": "2026-07-01", "end": "2026-07-10"},
    {"id": "later", "start": "2026-07-11", "end": "2026-07-20"}
  ],
  "platform_daily": [
    {"business_date": "2026-07-01", "platform": "平台A", "orders": 100, "paid_amount": 5200, "promo_spend": null}
  ],
  "store_period": [
    {"period": "earlier", "platform": "平台A", "entity_id": "store-1", "orders": 50, "paid_amount": 2600}
  ],
  "product_period": [],
  "promo_daily": [],
  "inventory_snapshot": [],
  "fulfillment_daily": [],
  "coverage": [
    {"collection_date": "2026-07-01", "family": "orders", "file_count": 1, "row_count": 200, "schema_fingerprint": "..."}
  ]
}
```

`platform_daily` 必须在 `business_date × platform` 上唯一。重复主键直接让质量门失败，不能静默相加。

`store_period` 和 `product_period` 可以包含同一实体的多条原始记录，但必须先聚合全部合格实体，再做排名。某个实体没有出现在其中一个榜单或导出中，只能标记为 `not_observed`，不能补成零，也不能进入精确变动排名。

## 数据质量门

发现以下问题时停止深度解释：

- 必填字段缺失；
- 日期无效；
- 订单量或支付字段为负数；
- 平台日表主键重复；
- 指标定义互不兼容。

发现以下情况时警告并调查：

- 业务日期缺口；
- 推广或退款只有部分覆盖；
- 文件数、行数或 SKU 数量突变；
- 相邻批次字段结构发生变化；
- 单均件数等指标明显异常；
- 分子和分母来自不同平台、日期、归因窗口或实体范围。

缺失、不适用、无法获得、被隐藏和真实零值是不同状态，适配器必须保留。只有分子和分母属于同一合格总体时才计算比例。

## 深度分析阶梯

运行 `scripts/analyze_operational_facts.py`，按以下顺序解释确定性结果：

1. 总体规模；
2. 每日趋势；
3. 阶段对比；
4. 平台贡献；
5. 订单量与每单支付分解；
6. 阶段内部的前半段和后半段；
7. 完整聚合后的店铺与商品变动；
8. 退款、推广、库存、履约和覆盖异常；
9. 验证动作。

脚本把突变标记为 `change_point_candidate_not_cause`，意思是“变化点候选，不代表原因”。没有独立证据时，不能把它改写成活动效果、代理问题或平台变化导致。

聚合表只能支持记录到的经营事实，不能据此推断运营人员心态、组织能力、平台政策变化或经营策略。原因判断至少需要与同一对象和时间轴匹配的规则、活动、决策日志、执行记录或实体映射；否则保留多个候选并给出核查顺序。

`promo_spend / paid_amount` 是“推广支出占支付额比例”，不是 ROAS。

## 交付物

主要交付物是可筛选、可下钻的 Excel；HTML 是简要阅读版。有对应事实时，工作簿包含：

- `说明与口径`；
- `经营总览`；
- `平台日表`；
- `阶段对比`；
- `店铺变动`；
- `商品变动`；
- `推广`；
- `库存与履约`；
- `数据质量`；
- `原始事实索引`。

Excel 使用表格对象或动态范围，冻结表头、启用筛选，并让平台维度出现在所有相关工作表和图表中。禁止把最后一行写死。交付前扫描公式错误，并把工作簿合计与 `operational_analysis.json` 对账。

对账结果写入隐藏工作表 `_corpus_lens_validation`，至少包含 `metric`、`workbook_value`、`analysis_value`、`difference` 和 `status`，所有交付行都必须是 `PASS`。

页面测试至少覆盖不大于 400 像素的手机宽度和不小于 1200 像素的桌面宽度，结果保存到 `viewport_qa.json`，然后运行 `scripts/validate_operational_outputs.py`。

HTML 展示决策摘要、平台切换、少量诊断图、明确边界和优先动作。它不是第二份 Excel，也不能隐藏审计 Excel 结果所需的重要证据。
