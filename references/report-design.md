# Data Lens 报告设计规范

## 1. 这份报告给谁看

- 产品形态：帮助用户做下一步决策的中文分析报告，不是后台、网站首页或技术审计页面。
- 主要读者：不需要理解数据契约和程序术语的创作者、运营人员与业务负责人。
- 核心任务：先看最重要的结论，再查看证据覆盖、差异和原因，最后明确现在做、接着做、以后做。
- 主题世界：随分析对象变化的证据型编辑手册。公众号复盘可以像内容编辑台；混合资料分析更像研究档案与生产链手册，但共享同一套可读性规则。

## 2. 选定风格：内容复盘手册

采用克制的编辑手册风格，不做 SaaS 仪表盘、营销落地页或技术证据账本。

- 报告头部只说明业务问题和真实资料范围，不展示路线 ID、契约版本、分析深度、文件哈希或程序状态。
- 目录是阅读指南，按照三至四个阅读阶段分组，使用普通用户能理解的问题或结果描述。
- 目录不得直接出现“口径与覆盖”“完整发现”“分析模块”“限制与未知”“方法与证据”等内部结构名称。
- 原始证据 ID、本机路径、哈希、方法文件和运行记录只放在 `run_manifest.json`，不出现在可见 HTML 中。
- 页面中的依据使用“后台阅读数据”“文章首屏原文”一类中文标签，不展示 `E01` 之类编号。
- 影响结论理解的限制，可以在报告末尾用“看结论前要注意”呈现，但不放进主目录。

## 3. 视觉规则

- 使用温和纸张底色和深色正文，森林绿只标记决策、依据和可执行动作。
- 桌面目录宽度保持在 232—248px，使用分组导航和足够大的点击区域，不给每条目录都加横线。
- 主阅读区域的有效行宽控制在 760—860px，整页最大宽度约 1180px。
- 间距只使用 4、8、12、16、24、32、48px，不使用按屏幕高度撑开的空白区域。
- 卡片只用于真正需要对照或单独行动的内容。普通发现使用编辑式列表，不做卡片套卡片。
- 允许一组紧凑的数据概览，只展示实际审阅量、结论性质、成熟度、生产链或行动优先级；不得用文件数量伪装共识，不得加入无决策价值的装饰图。
- 不使用纯装饰的章节编号。标题、标签和颜色都必须帮助理解内容。
- 正文不小于 15px，目录点击区域不小于 44px，移动端 360px 不得横向溢出。

## 4. 目录规范

每一份正式的 `deep_analysis.json` 都要提供 `presentation.toc_groups`，目录名称必须是面向读者的大白话。

报告通常使用三到四段阅读路径。公众号复盘可使用：

1. 先看结论
2. 看数据表现
3. 拆文章内容
4. 决定下一批

混合资料报告可使用“先看答案—看清问题—开始整理”，并优先放入生产链、成熟度、断点和下一步验证。

目录只放会影响阅读和决策的章节。方法记录、证据索引、限制清单和待回答问题不占用目录位置。

当报告包含抽样或实验时，可以使用“这次样本能说明什么”“下一轮怎么验证”等名称。不得直接展示 `sampling`、`evidence_coverage`、`experiments` 等字段名。

## 5. 内部产物与用户页面的分界

`deep_analysis.json`、验证文件和 `run_manifest.json` 必须保持完整和可追溯。HTML 是给用户阅读的版本。

隐藏程序使用的证据编号、哈希和方法文件，不属于缩短分析。事实、解释、反例、边界、文章对比、行动建议和影响判断的必要提醒，仍然必须完整展示。

实验卡只展示用户执行所需的变量、对照、指标、周期、判定规则和停止条件。目的识别关键词、路由置信度及脚本状态继续留在内部产物。

## 6. 通用流水线，不写单次任务脚本

目录覆盖与补样使用 `select_samples.py`、`expand_mixed_sample.py`；原始证据抽取使用 `extract_source_evidence.py`、`render_pdf_samples.py`；语义审核使用标准批次包和 JSONL 台账；报告骨架使用 `init_deep_analysis.py`。单次任务可以包含针对资料的判断，但不得再生成把本次结论硬编码进 Python 的脚本。重复出现的机械步骤必须收回 Skill，并在 Skill 内测试。
